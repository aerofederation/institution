## 1. Environment

Put credentials in `.env.local` (preferred) or `.env`. Both are gitignored;
neither is ever committed. Scripts read `.env.local` first, then `.env`, and a
variable already exported in the shell beats both.

```bash
npm run check:env
```

Reports which variables are set without printing any secret value.
`SUPABASE_PROJECT_REF` is derived automatically from `NEXT_PUBLIC_SUPABASE_URL`,
so it does not need to be supplied.

`SUPABASE_DB_PASSWORD` — the database password from Project Settings → Database,
*not* the service role key — is what opens the direct connection used by
`db:push`, `db:repair` and `db:types`. All Supabase, SMTP and AI variables are
currently configured.

## 2. Link and migrate

```bash
npm run db:push     # applies supabase/migrations over a direct connection
npm run db:repair   # marks already-deployed migrations as applied
```

`supabase link` needs a **personal access token** (`SUPABASE_ACCESS_TOKEN`),
which is separate from the database password. It is not configured here, so
`db:push` uses `--db-url` instead and skips linking entirely. Everything works
with the database password alone.

> **When a schema was deployed without recording itself.** That was the case
> here: the tables existed but `supabase_migrations.schema_migrations` was
> empty, so `db:push` tried to re-run `001` and failed on an existing enum.
> `db:repair` fixes it by marking versions applied without running them:
>
> ```bash
> npm run db:repair -- 20260101000014   # mark all EXCEPT 014 as applied
> npm run db:push                       # then apply 014 alone
> ```

Confirm the remote matches the migration files. `db:diff` needs Docker, which is
unavailable here, so drift is detected by `npm run db:types:check` instead —
it introspects both sources and diffs every table, column and enum.

## 3. Database types

```bash
npm run db:types         # introspect the hosted database
npm run db:types:local   # introspect supabase/migrations, in-process
npm run db:types:check   # generate from both and diff them
```

`supabase gen types` is not used: its `--db-url` mode needs Docker and its
`--linked` mode needs an access token. The generator here reads the catalog
directly with the database password, running the *same queries* against either
source — which is what makes `db:types:check` meaningful.

`db:types:local` regenerates the same file from the migration files alone, with
no credentials, by applying them to an in-process PostgreSQL. `db:types:check`
compares the two and fails if they disagree — which is how a migration that was
never pushed, or a table edited by hand in the dashboard, gets caught.

## 4. Why provisioning is explicit

Migration 006 installs `on_auth_user_created` on `auth.users` to build a profile
whenever an account is provisioned. **That trigger cannot do the job**, and the
reason is not obvious — it cost a full debugging cycle here, so it is recorded
in full.

The trigger is installed, and it works. A direct SQL insert into `auth.users`
carrying `app_metadata` fires it and produces a correct profile. But an account
created through the **GoTrue admin API** produces no profile at all — while
`raw_app_meta_data` visibly contains `afi_role` afterwards.

GoTrue inserts the user row **first** and applies `app_metadata` in a
**subsequent UPDATE**. An `AFTER INSERT` trigger therefore always observes empty
metadata, has no role or tenant to act on, and correctly does nothing.

This is not a permissions problem, and re-installing the trigger does not fix
it. Every account the application will ever create goes through that API, so an
`auth.users` insert trigger can never be the provisioning mechanism.

**Migration 014 is the answer.** `public.provision_profile()` lives in a schema
this project owns, is callable only by the service role, is idempotent, and
refuses `HQ_ADMIN`. It is the path the provisioning services, the seed and the
verification suite all take. The trigger remains as a backstop for direct SQL
inserts, where it does work.

Verified live: *"every provisioned account receives a profile — via
provision_profile() — the supported path"* and *"no HQ_ADMIN profile can be
created through the Auth API — refused by provision_profile()"*.

## 5. HQ administrator bootstrap

`HQ_ADMIN` is the most privileged role on the platform and has no path through
the application, the Auth API, or any seed script. Three independent mechanisms
enforce that: the provisioning trigger refuses the role, `provision_profile()`
refuses it, and `prevent_privilege_escalation()` refuses any change to
`profiles.role` arriving as `authenticated`.

It is created deliberately, by an operator, from a machine with database
access:

```bash
HQ_EMAIL=you@example.com HQ_PASSWORD='…' npm run bootstrap:hq
```

The script creates the Auth user, writes the `HQ_ADMIN` profile over a direct
database connection (the only path the three guards above leave open), mirrors
the role into `app_metadata` for middleware routing, and records the act in the
audit log. Credentials come from the environment and are never written to disk
or printed.

It refuses to convert an existing tenant account to HQ — use a separate address.
Re-running is safe and idempotent per email address; on an existing account it
resets the password and confirms the email.

`supabase/seed/bootstrap_hq_admin.sql` remains as the pure-SQL equivalent for
an operator working only in the Supabase SQL editor, where the Auth user must be
invited through the dashboard first.

**Password policy.** The Auth admin API does not apply the application's own
rules, so a weak password can be set here. The script warns when one does not
meet the policy in `lib/validation/common.ts` (12 characters, upper, lower,
digit) — worth heeding, because the in-app reset flow will later refuse a value
the bootstrap accepted.

## 6. Seed development data

```bash
npm run db:seed
```

Creates one clearly-marked demonstration institution (`demo-` slug, `(Demo)`
name suffix, `example.test` addresses) with an administrator, three teachers,
six students and a full academic structure.

- It **refuses to run** against a hosted database unless `--allow-remote` is
  passed. The guard checks the Supabase host, not `NEXT_PUBLIC_APP_URL` — the
  app URL says where the browser points, not which database receives the rows.
- It creates **no HQ administrator**, ever.
- Accounts are left `INVITED` with no password, exactly as real provisioning
  leaves them.
- If HQ has not been bootstrapped, the demo institution stays `PENDING` and
  its users cannot sign in. That is the honest state; the approval workflow in
  Phase 9 is what moves it.

## 7. Verification

```bash
npm run verify:supabase     # 40 checks against the live project
npm run verify:application  # 23 checks on the public application flow
npm run verify:cleanup      # remove leftover fixtures if a run was interrupted
```

`verify:application` drives the institution application end to end as an
ANONYMOUS caller — the same anon key a browser holds — because that is the only
way to know the public write path works and is actually constrained. It asserts
the refusals as carefully as the successes: a wrong draft token, direct table
access, a forged document path, resubmission after submission, a mismatched
tracking email, a wrong code, and code reuse all have to fail.

Two bugs reached the hosted project and were caught only by this script, both of
the same shape — PL/pgSQL does not resolve identifiers or check types when a
function is created, only when its body runs, so a migration can apply cleanly
and still be broken:

  * a `CASE` returning untyped literals against an enum column (fixed in 017);
  * a parameter named the same as a column, which PL/pgSQL refuses as ambiguous
    (fixed in 018).

A successful `db push` is not evidence that a function works.

`verify:supabase` creates two throwaway institutions and nine accounts prefixed
`zzverify`, exercises them through the real APIs — GoTrue, PostgREST, Storage —
and removes everything in a `finally` block. It covers connection, schema
parity, auth, profile provisioning, role protection, tenant isolation,
anonymous denial, storage policies, audit logging, the application state
machine, and the database functions and triggers.

Nothing is asserted from reading code.

## 8. Email

```bash
npm run verify:email
```

Opens the SMTP connection and completes authentication. **It does not send a
message** — a verification script that emails somebody is one that can be aimed
at an arbitrary address. Reports `NOT CONFIGURED` and exits 0 when SMTP
variables are absent, since an unconfigured optional service is not a failure.

Template rendering, escaping and the "never transmit a password" rule are
covered by `tests/unit/email.test.ts`, which needs no network.

## 9. Local checks — no credentials needed

```bash
npm run verify   # lint + typecheck + build
npm test         # 116 tests: unit, integration, RLS
```

The RLS suite applies the real migration files to an in-process PostgreSQL
(PGlite) and drives them as `anon` and `authenticated` the way PostgREST does.
It is a test harness, not a second database — Supabase remains the only backend,
and nothing under `app/`, `lib/` or `services/` imports it.
